# Подготовка production

Конфигурация подготовлена локально. Запуск на VPS, DNS, выпуск сертификата и внешние интеграции в рамках исправлений не выполнялись. Не использовать существующие каталоги или Compose-проекты других сервисов.

1. Сначала проверить CI, тестовую установку и восстановление резервной копии. В production применять только проверенную версию; сохранить текущую версию образов для отката.
2. Создать отдельный каталог Focus Analytics и `.env.production` по примеру. Установить права 600. Сгенерировать уникальный случайный пароль БД (например, 32 байта в hex), одинаковый в `POSTGRES_PASSWORD` и `DATABASE_URL`. Не использовать демонстрационных пользователей. Настроить настоящий HTTPS origin.
3. Подготовить сертификат домена: `fullchain.pem`, `privkey.pem`; указать `TLS_CERT_DIR`. Продление сертификата — отдельная инфраструктурная настройка, после продления нужен reload nginx. Привязку домена и доступность портов 80/443 проверить заранее.
4. Проверить конфигурацию без вывода секретов: `docker compose --env-file .env.production -f docker-compose.prod.yml config --quiet`. На тестовом хосте собрать образы, проверить `nginx -t`, HTTPS, вход, viewer/admin права, logout, readiness и все рабочие страницы. В этой сессии Docker runtime и TLS не проверены.
5. Перед изменением существующей БД остановить worker, сделать backup и restore drill. `ops/backup.py backup <new.dump>` использует libpq-переменные и `PGPASSFILE`; пароль не передавать в командной строке. `verify` проверяет формат, `restore-drill <file> --database focus_restore_<unique>` восстанавливает в НОВУЮ БД и не удаляет исходную. После восстановления сверить `alembic_version`, количество строк и ключевые отчёты.
6. Только после разрешения на deploy: `docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build`. API выполняет миграции; worker стартует после readiness API. Наружу открыты только nginx 80/443. При ошибке миграции остановиться, не делать `stamp head` и не удалять таблицы.
7. Сверить sync каждой фазы, возраст данных, охват Timeman, число ошибок и корректность бизнес-настроек. Наличие HTTP 200 у API не доказывает свежесть данных. Live Bitrix проверять только разрешёнными read-only методами.

Новая миграция `0008` сохраняет повторные состояния сделок. Её downgrade намеренно откажется при повторных payload: автоматическое удаление истории запрещено. Откат с изменением схемы требует отдельной проверки или восстановления проверенной резервной копии, с учётом данных после её создания.

Резервные копии хранить вне диска сервера, ограничить доступ, настроить ротацию и регулярный restore drill. Расписание копирования, срок хранения и внешнее хранилище ещё нужно настроить на выбранной инфраструктуре. Графики, регламент, планы и дата включения официального контроля должны быть утверждены владельцем продукта.
