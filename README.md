# Focus Analytics

Внутренняя веб-система аналитики отдела продаж. Этап 1 — фундамент: Bitrix24 (read-only), PostgreSQL, синхронизация, KPI, веб-панель.

Production-сервисы `/opt/prosrochka` и `/opt/focusgroup-sla` **не затрагиваются**.

## Стек

| Слой | Технологии |
|------|------------|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 async, Alembic, Pydantic v2, httpx |
| Worker | APScheduler / отдельный процесс синхронизации |
| Frontend | Next.js (App Router), TypeScript, Tailwind, TanStack Query, Recharts |
| БД | PostgreSQL 16 |
| Infra | Docker Compose |

## Быстрый старт (Docker)

```bash
cp .env.example .env
# Задайте SESSION_SECRET. При наличии webhook — BITRIX_WEBHOOK_URL и BITRIX_PORTAL_URL.

docker compose up --build -d
```

Создание администратора:

```bash
docker compose exec backend python scripts/create_admin.py --email admin@company.local --password "YourSecurePassword"
```

Откройте http://localhost:13000 → `/login`  
(порты на хосте: frontend `13000`, API `18000`, PostgreSQL `55432` — чтобы не конфликтовать с другими локальными стеками).

API: http://localhost:18000/api/v1/health  
Документация API: http://localhost:18000/docs

```bash
cd backend
```

Worker (отдельный терминал):

```bash

```


```bash
cd frontend
cp .env.example .env.local
npm install
npm run dev
```

http://localhost:3000 — Next.js проксирует `/api/*` на backend (`API_INTERNAL_URL`).

## Переменные окружения

См. [.env.example](.env.example).

| Переменная | Назначение |
|------------|------------|
| `DATABASE_URL` | PostgreSQL (asyncpg) |
| `BITRIX_WEBHOOK_URL` | Incoming webhook Bitrix (read-only) |
| `BITRIX_PORTAL_URL` | URL портала для ссылок «Открыть в Bitrix» |
| `BITRIX_CATEGORY_IDS` | Воронки, по умолчанию `1,39` |
| `SESSION_SECRET` | Секрет сессий |
| `DEMO_MODE` | Загрузка помеченных DEMO-данных при старте API |
| `APP_TIMEZONE` | `Europe/Moscow` — границы суток для KPI |
| `TELEGRAM_BOT_TOKEN` | Токен бота для ежедневного дайджеста (пусто — выключен) |
| `TELEGRAM_CHAT_ID` | Чат руководителя/отдела для общего дайджеста |
| `DIGEST_TIME`, `DIGEST_DAYS` | Время (`09:00`, в `APP_TIMEZONE`) и дни (`mon-fri`) отправки |
| `DIGEST_STALE_DAYS` | Через сколько дней без движения сделка попадает в «стоят» (по умолчанию 7) |
| `DIGEST_TOP_N` | Сколько сделок показывать в каждом списке (по умолчанию 5) |

Секреты не коммитить и не логировать.

## Воронки и скорость сделок

Страница «Воронки» показывает по каждой воронке и выбранному периоду (по умолчанию 90 дней), по всему отделу или по одному менеджеру:

- **конверсию по этапам** — сколько сделок, созданных в периоде, дошли до этапа или дальше, и где самый большой отсев;
- **время на этапах** — медиану и среднее по переходам, завершившимся в периоде, и сколько сделок стоит на этапе сейчас;
- **долю выигранных** и **цикл сделки** (от создания до закрытия) по сделкам, закрытым в периоде;
- **где теряем** — на каком этапе была сделка перед проигрышем;
- **разбивку по менеджерам**.

История переходов берётся из Bitrix методом `crm.stagehistory.list` (только чтение). Это точное время каждого перехода, в том числе за прошлое. Worker забирает её на каждом цикле синхронизации; первый запуск загружает всю историю. Если на портале метод недоступен, воронка строится по изменениям этапов, замеченным при синхронизации, и страница честно об этом предупреждает.

Проверить метод на своём портале:

```bash
docker compose exec backend python scripts/bitrix_stagehistory_probe.py
```

## Зависшие сделки, скорость реакции, просрочки

- **Зависшие сделки** — сделка находится на стадии дольше срока. Сроки по умолчанию взяты из ответов к ТЗ и подставляются по названию стадии: «Не обработан» и «Взят в работу» — 1 рабочий час, «Недозвон» — 7 дн., «Квалификация» и «КП с расчётом» — 10 дн., «Поставлен в график / Монтаж» — 30 дн., «Ждём итоговую оплату» — 7 дн. Администратор меняет любой срок на этой же странице: рабочие часы, рабочие дни или календарные дни, либо «не отслеживать».
- **Рабочее время** — `WORK_DAYS` (`mon-fri`), `WORK_HOURS` (`09:00-17:00`), `COMPANY_HOLIDAYS` (`12-26..01-11`, повторяется каждый год). Заявка, пришедшая в пятницу в 16:50, к 09:20 понедельника ждёт 30 рабочих минут, а не 64 часа.
- **Скорость реакции** — рабочее время от создания сделки до перевода из первой стадии и до выхода из стадий реакции (первый контакт). Нормы — сумма сроков этих стадий.
- **Просроченные дела** — дела со сроком в выбранном периоде, которые висят до сих пор или закрыты позже срока; видно, на сколько просрочено и когда закрыто.

Время закрытия дела раньше бралось из `END_TIME` — это плановое окончание, а не факт. Теперь берётся `LAST_UPDATED` на момент, когда дело впервые увидели закрытым. Миграция `0005` очищает старые значения, их заполнит ближайшая полная синхронизация.

## План / факт

Цели продаж администратор заводит на странице «План / факт». Цель задаётся на весь отдел или на конкретного менеджера, на неделю, месяц, квартал, год или произвольные даты.

- **Факт** — сумма выигранных сделок за период цели. Правило то же, что у KPI «Успешно закрыто»: семантика этапа success и `CLOSEDATE`, а если его нет — дата изменения. Для цели менеджера учитываются только его сделки.
- **Прогноз** — текущий темп продаж, продлённый до конца периода. Пока прошло меньше 20% периода (и меньше 3 дней), прогноз не показывается, а статус цели — «Начало периода»: по одной сделке на второй день месяца прогноз был бы бессмысленным.
- **Статусы:** «В графике» — прогноз не ниже плана; «Под угрозой» — прогноз 90–100% плана; «Отстаём» — ниже 90%; «Выполнен» и «Не выполнен» — когда период закончился.

План отдела выводится на дашборде, а выполнение плана — в утреннем дайджесте: общем и личном у каждого менеджера.

## Ежедневный и недельный отчёт

- **Дневной** — в `REPORT_DAILY_TIME` (20:00) по рабочим дням, итоги текущего дня. Выходные и общий отпуск пропускаются. Сравнение — с предыдущим рабочим днём (понедельник сравнивается с пятницей).
- **Недельный** — `REPORT_WEEKLY_DAY` в `REPORT_WEEKLY_TIME` (понедельник 09:00), за прошлую неделю пн–вс; сравнение с позапрошлой.
- **Месячный** — по кнопке на странице «Отчёты».

Что входит в отчёт: новые, выигранные (с суммой) и проигранные сделки, просрочки за период, незакрытые просрочки, зависшие сделки, медиана реакции, выполнение плана. Ниже — разбивка по менеджерам (вместе с долей сделок с просрочкой и долей зависших), сделки, требующие внимания, сделки без следующего дела, а в недельном и месячном — проблемные этапы.

Все отчёты сохраняются в архиве на странице «Отчёты», даже если Telegram не настроен. В Telegram отчёт уходит один раз в личные чаты из `TELEGRAM_REPORT_CHAT_IDS` (Максим, Андрей через запятую), а если список пуст — в `TELEGRAM_CHAT_ID`. Администратор может сформировать отчёт заново и отправить его вручную.

## Ежедневный дайджест в Telegram

Каждое утро worker отправляет:

- **в общий чат** (`TELEGRAM_CHAT_ID`) — итоги вчерашнего дня (новые и выигранные сделки), просроченные дела, сделки без следующего дела, сделки без движения и разбивку по менеджерам;
- **каждому менеджеру с указанным chat id** — его личный список со ссылками на сделки в Bitrix.

Настройка:

1. Создайте бота у [@BotFather](https://t.me/BotFather) и запишите токен в `TELEGRAM_BOT_TOKEN`.
2. Добавьте бота в чат руководителя или отдела и напишите в чат любое сообщение. Откройте `https://api.telegram.org/bot<токен>/getUpdates` и возьмите `chat.id` (у групп он отрицательный). Запишите его в `TELEGRAM_CHAT_ID`.
3. Для личных сообщений менеджер пишет боту `/start`. Его chat id (тоже из `getUpdates`) администратор вводит на странице менеджера в панели.
4. Перезапустите worker: `docker compose restart worker`.

На странице «Система» администратор видит статус дайджеста, может открыть предпросмотр и отправить дайджест вручную. Автоматически дайджест уходит не чаще одного раза в день. Если данные из Bitrix устарели больше чем на 3 часа, в дайджесте появляется предупреждение.

## Важно

- Все операции с Bitrix — **только чтение**.
- Изменения через polling — **наблюдаемые**, не полная историческая лента.
- Сделки без следующего дела — **факт**, не нарушение SLA.
- Реальная синхронизация с Bitrix возможна только после заполнения `BITRIX_WEBHOOK_URL`.
